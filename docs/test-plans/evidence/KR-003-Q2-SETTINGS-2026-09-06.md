## Established versus inferred cause

**Established classification/enforcement mechanism:** the ten blocking transitions are caused by `identity=ORDINARY_APP` events, not UNKNOWN or
an OWN_PACKAGE-to-SAFE feedback loop. In the inspected policy, ORDINARY_APP means a nonblank event package that is neither the spike nor in the
existing safe set (which already includes the standard Settings package). The resolver changes SAFE_SYSTEM to ORDINARY_APP and attaches the
overlay. This supports the owner's hypothesis at the **event-classification mechanism** level; it does not identify each actual destination app.

**Established recovery mechanism limitation:** the Settings button calls `startActivity(ACTION_SETTINGS + FLAG_ACTIVITY_NEW_TASK)` but does not
itself enter a recovery state or remove the overlay. It relies on a later known-safe window event. The final four handlers and launch-call returns
are captured; no such event follows, so ordinary enforcement stays applied. There is no evidence of an attach/remove exception in this run.

**Not established:** exact destination packages/components, task-stack contents, whether a retained Settings task resumed a blocked child screen,
OEM launch suppression, or whether a foreground change occurred without the subscribed window event. Each root-cause attribution remains
**UNSPECIFIED**. The telemetry cannot prove a one-to-one map from the nine failed UI labels to the ten ordinary transitions.

Task reuse is a credible hypothesis, not a diagnosis: Android documents that `FLAG_ACTIVITY_NEW_TASK` can restore an existing task's prior state.
It is not an unconditional instruction to recreate the top-level Settings UI. Changing flags can alter/destroy activity-stack state, so do not
blindly add CLEAR_TOP/CLEAR_TASK or treat intent dispatch as a recovery guarantee.
[Official task/intent guidance](https://developer.android.com/guide/components/activities/tasks-and-back-stack#IntentFlags), verified 2026-09-06.
