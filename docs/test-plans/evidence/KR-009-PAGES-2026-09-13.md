## Implemented contract

The existing locked repeatable-read PostgreSQL gateway freezes canonical policy, version, trusted UTC, lifecycle and outcomes in one private per-device/epoch cache. Cursor validity is five minutes. Pages contain at most 100 outcomes / 64 KiB; one cache contains at most 1,000 outcomes / 256 KiB. `history_pruned` retains the latest authoritative high-water even when older detail is omitted. First-page repeat is identical while canonical version, cursor, identity/epoch, period/zone and credential generation still match. Later pages never use newer canonical values/outcomes. Invalid cursor syntax is 400; stale/expired/replaced/foreign sequence is generic 410 `SNAPSHOT_RESTART_REQUIRED`. The cache slot is bounded and replaced/deleted with the device; TTL is access expiry, not an unimplemented physical-cleanup promise.

Child validation compares JSON values independent of object-key order, authenticates own device/epoch and checks all frozen fields. It retains only the first/current page in memory and a tiny non-authoritative checkpoint on disk. It never stores command history. A restart begins a complete first-page request using the durable ledger; an expired sequence restarts once, then uses retry. Only after all pages validate does the existing Room policy/accounting/immutable ACK transaction commit. Approved KR-008 A/B uncertainty remains unchanged.

Restart, actual Activity resume, live ConnectivityManager callback and post-local recovery feed one coordinator: at most one active sync and one follow-up per group. The checksummed AtomicFile retry state contains only identity binding, pending/stopped/reason, attempt, boot and monotonic due/delay. Backup recovery and corruption handling do not touch policy. Storage recovery may release STORAGE stop only; AUTH/PROTOCOL remain stopped until explicit supported recovery. Full-jitter retry uses 1-second exponential base, five-minute cap while runnable; Retry-After seconds or server-Date-relative HTTP dates form a bounded floor. No device wall clock supplies accounting or retry authority across boots.

One unique constrained periodic WorkManager request (15-minute interval, five-minute initial delay) is persisted before HTTP. Recovery also polls canonical state with no pending local intent, making push unnecessary. WorkManager dispatch is best effort and can run later; this is not an exact timer, foreground service or scheduling-latency claim. Existing KR-007 rotation/removal and KR-008 Room/ACK stay authoritative. Release manifests retain only the added network-state/wake/boot permissions required by recovery; the transitive foreground service and its permissions are removed.

Official references: [WorkManager stable 2.11.2](https://developer.android.com/jetpack/androidx/releases/work), [constraints/delay/retry semantics](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work). No FCM SDK, project, registration, provider address or dispatcher is selected/implemented.
